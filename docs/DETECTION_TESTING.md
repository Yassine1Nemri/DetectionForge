# Detection testing

## Phase 1 semantics

Tests are explicitly `offline`. They evaluate canonical Sigma fields in synthetic events. They never execute PowerShell, ingest data, connect to Splunk, or interpret generated SPL. Fixtures are reproducible examples, not production security events.

The evaluator traverses the parsed pySigma condition AST. It supports named field mappings, string/integer/boolean equality, contains/startswith/endswith string modifiers, optional all, lists, Boolean AND/OR/NOT, and selector quantifiers expanded by pySigma. String matching is case-insensitive. Unknown modifiers, explicit wildcard values, regexes, field references, nulls, floats, keyword searches, correlation, and collection documents are rejected. Preflight checks all selections, including unused or short-circuited branches; unsupported data cannot become a passing result.

Only Windows Sysmon process-creation fixtures are supported initially. Every event requires canonical integer EventID 1. Canonical fields are evaluated before deployment field mappings. Real Splunk extractions and comparisons can differ, so offline success does not establish SPL efficacy.

## Dataset contract

See `test_datasets/malicious/powershell_encoded.json` and `test_datasets/benign/powershell_admin.json` for complete examples. Required properties:

- `id`, `rule_id`, category (`malicious` or `benign`), technique, exact rule `logsource`.
- Nonempty `events` (maximum 1000), each with unique ID, timezone-aware timestamp, and scalar fields (string/integer/boolean).
- `expected_event_ids`, a unique subset of the event IDs.
- `expected_detection`, equal to whether the expected ID set is nonempty.

A malicious-category fixture must expect at least one match; a benign fixture must expect none. Mixed events are permitted in positive fixtures, with truth defined per event. A malicious fixture may include nonmatching control events. Client dataset and selected rule UUIDs must agree. Its technique must appear among the rule's tags; this checks consistency, not authoritative ATT&CK catalog validity.

API: POST `/api/tests/run` with `rule_id` and exactly one of `dataset_id` (a bundled identifier) or `dataset` (a complete validated dataset). Custom datasets are supported through the API; the UI selects bundled datasets. The service creates the run UUID and keeps source version, dataset, duration, and result snapshots. Unsupported tests return an error and do not create successful history entries.

## Verdict and metrics

PASS requires exact actual/expected event-ID set equality and agreement with expected detection. The report lists missing and unexpected IDs and the actual matched events. Disabled rules cannot run. Editing or changing enabled state creates a new rule version; current-version status resets to untested. Older evidence remains downloadable.

For expected set E, actual set A, and all input IDs U:

- TP = |A ∩ E|; FP = |A − E|; FN = |E − A|; TN = |U − (A ∪ E)|.
- Precision = TP/(TP+FP), or null if undefined.
- Recall = TP/(TP+FN), or null if undefined.
- Dashboard fixture pass rate = passing stored runs / all stored runs, or null if no runs. This includes historical versions and repeated executions, not unique detection coverage.

The dashboard's tested/untested detection counts use the current version only. The latest test status represents the most recent fixture execution, not a suite-wide verdict. Invalid imports are rejected; the stored invalid-rule count is therefore zero. Imported rules can be valid Sigma while unsupported by the offline evaluator or current conversion profile.

## PowerShell scenario: T1059.001

The experimental rule detects powershell.exe or pwsh.exe with spaced `-EncodedCommand` or `-enc` command-line switches. Positive fixtures include both switch forms and an unrelated cmd.exe control. Negative fixtures contain service enumeration and an inventory script.

The encoded content represents harmless text. No sample commands are executed. Limitations: renamed binaries, alternate encodings, switch abbreviations, tab delimiters, executable naming variations, and other PowerShell abuse can evade these exact patterns. Legitimate encoded administrative commands can trigger them. A passing benign fixture does not establish an operational false-positive rate or complete technique coverage.

Run all repository checks:

```bash
.venv/bin/python scripts/check_offline.py
.venv/bin/pytest -c backend/pyproject.toml backend/tests -q
```

The script writes real evaluation output to `reports/offline-report.json` and fails nonzero on invalid input or mismatch. Reports generated by the script are independent of the database and are not fabricated UI history.

## Planned live verification

Phase 2 must explicitly select live mode, ingest into an allowlisted dedicated test index, stamp a server-generated run ID and per-event fixture ID, wait for ingestion visibility, execute a bounded query scoped to BOTH index and run ID, and compare exact event identifiers. Timeouts, authentication errors, or missing ingestion are errors; they must never silently invoke offline evaluation. A public CI runner must not connect to a workstation Splunk service.
